# Unity UI14 对照独立 Demo V3：移植盘查

日期：2026-10-26。性质：只读设计与源码审计；本轮仅新增本报告。

## 结论

**当前版本不能视为 Demo V3 的一比一移植。** 顶层框架、地块分区、容量图形和部分操作已经落地，但不少详表与对象检查仍沿用旧实现。缺口同时涉及版式、数据口径、导航状态和功能可达性，不能只靠换图标、调字号解决。

最应先处理的四类问题：

1. 首次结算前，部分详表把缺失的实际数据显示为确定的零或 100%，且同页可能互相矛盾。
2. 从详表定位地图后不能继续操作地块；深入建筑再返回还可能丢失详表状态。
3. 任务处理入口没有完整携带目标、资源和服务筛选，部分入口落到错误工作区。
4. 建造窗口漏掉 Demo 的主要变化／投入约束比较区域，仍以长句堆叠候选信息。

这些问题不要求推倒已有模拟和命令系统。应保留真实规则和已完成的 UI 结构，补齐设计对应关系。

## 对照范围与证据边界

- 参照：`prototypes/met-ui-lab/delivery/MET-UI-Lab-v3/source/src/` 冻结源码及同目录交付的 `index.html`，不以不断演变的原型工作目录代替交付基线。
- Unity：当前 checkout 的 `unity/METLivingWorld/Assets/City/UI/`。本轮逐文件比较了 `v0.7.0-ui.14` 中的 41 个 UI C# 文件，均与当前文件一致，因此以下结论对应 UI14 的 UI 源码。
- 展示基准：最新约定的 2560×1440，独立 UI 缩放与字号；不追加移动端或小窗口适配范围。
- 用户最新的建造窗口截图确认了长句、重复信息、大片空白和超宽确认区的实际表现。其他条目主要通过对应实现和调用路径确认；本轮没有新启动 Player、浏览器或执行真人输入验收。
- 旧截图中的图标拉伸不能直接算作 UI14 未修问题；当前已有图标资源及等比例呈现修正。
- Demo 的场景数值、模拟推进工具、虚构容量和收益不是正式游戏规则。功能布局可以对齐，真实结算、运营商数量、来源和限制不能用假数据替换。
- 本轮未修改游戏代码、玩家存档或发布产物，保留原有未提交工作。

## 一、应优先修正的数据与操作问题

### 1. 首次结算前，详表将未知实际值显示成确定结果

**源码确认；正常的新建且暂停流程即可到达，不是极端存档情况。**

紧凑页已经检查是否有实际结算，显示“待结算”。详细人口页和电力页未统一采用这条规则：

- 人口概览的“实际口粮”可以用缺省比例显示 100%。
- 同页住户详情的空 `living` 数据又默认口粮 0%、失业 100%。
- 电力详表将空的供需指标显示为实际供给 0、需求 0、满足率 100%。

初始人口、健康等已存在的状态值仍然有效；应仅将尚无结算证据的实际分配值标为待结算，不能把全部初始状态清空。

证据：Unity [CityPages.cs:49](../../unity/METLivingWorld/Assets/City/UI/CityPages.cs)、[CityPages.cs:73](../../unity/METLivingWorld/Assets/City/UI/CityPages.cs) 的 `ResourcePage`／`PopulationPage`；与 `CityNavigationPages.cs:26–36,53–59` 的待结算分支对照。来源链为 `CitySession.New` → `Game.choose_origin` → `refresh_metrics`；实际生活与电力分配由后续 `Population`／`Sim.tick` 填入。`Economy/Progress.cs:14` 的食物比例缺省值不能充当实际分配凭据。

### 2. 从高级详表“定位”地图后，地块检查和操作被锁住

**源码确认。** 紧凑页定位和高级页定位走了不同的输入归属：

- 紧凑页进入地图可选择地块、显示左下信息并返回列表，已经实现。
- 高级施工表、档案来源等调用同一个 `InspectMapFromPage`，但 `_mapFromCompact` 为 false；此时隐藏地块面板，并拒绝选择地块／建筑。

因此玩家可以看到定位结果和返回入口，却无法顺着来源检查地块、暂停、升级。Demo 的实际对象定位允许继续使用地图。方案预测地图保持只读另有合理用途，不能把它与实际来源定位混为一类。

证据：Demo `App.tsx:40,65`；Unity `CityInterface.cs:130–143`、`CityTilePanel.cs:30`、`CityV3Workspace.cs:11`；实际入口 `CityConstructionManagement.cs:57`、`CityRecords.cs:24`。

### 3. 对象抽屉未移植，返回还会丢失高级模式

**源码确认。** Demo 检查建筑时保留当前工作区，在附属抽屉内展示对象。Unity 的来源／建筑按钮调用 `Navigate("building", id)`，清空并替换主内容。玩家不能同时看列表和对象原因。

另有明确状态缺陷：**施工详表 → 建筑与来源 → 返回**，历史栈只存页面与 context，未存高级模式；`Back` 按路由重新推断，`construction` 被推断为紧凑页，返回后丢失原展开状态。这不代表所有栏目状态保存都坏了，栏目切换和部分地图返回已有保存逻辑。

证据：Demo `App.tsx:39,76`、`compact/compact.css:80–81`；Unity `CityNavigationModel.cs:94–108`、`CityV3Workspace.cs:12–13`、`CityInterface.cs:175–176`、`CityBuildings.cs:8–17`。

### 4. 任务“处理”入口没有准确指向缺口，也没有流程回程

**源码确认。** 紧凑页将医疗、教育等目标统一送到居民首页，没有设置对应服务筛选；详细任务的目标路由又未覆盖医疗、教育，落到默认施工页。相同目标从不同层级进入，落点不同。

Demo 从目标发起操作会保留目标提示和“回到此目标”，Unity 没有对应的独立流程上下文。跨栏目的固定父级规则本身是对的，但不能替代目标回程。

证据：Demo `compact/destinations.ts:3–4`、`App.tsx:71`；Unity `CityV3Development.cs:60–64`、`CityTaskDetails.cs:37–42`。补齐路由应使用真实目标类型和服务／资源筛选，不另造目标判定。

### 5. 顶栏通货点击没有选中财政来源

**源码确认。** 其他资源会带入资源上下文；通货分支直接打开 `economy_home`，未更新 `_operatingEconomyResource`。结果可能继续显示默认食物或上次资源的贡献，虽然玩家刚点击的是通货。

证据：Demo `App.tsx:59`；Unity `CityWorkspaces.cs:76–80`、`CityNavigationPages.cs:24,53,60–62`。

## 二、建造窗口与视觉组织没有按 Demo 落地

### 6. 建造窗口漏了决策最需要的一块结构

**源码确认，用户最新截图也直接确认可读性问题。** Demo 的方案选项下方有两列：

- “此方案的主要改变”：对齐的变化值，先看差异。
- “投入与当前约束”：通货、材料、CP 并列，配库存、电力和具体限制。

Unity 目前是三个候选卡各自重复用途、槽位、说明、全部指标和费用，然后直接进入重抽与折叠的城市变化，没有上述双栏。因此大量信息塞进候选卡，而中下部没有形成有效比较区域。

底部 Demo 将成本与操作按钮分区；Unity 取消按钮之外的剩余宽度都交给确认按钮。截图里的巨大按钮和空白无法通过增加图标补回来。

证据：Demo `App.tsx:108–110` 的 `proposal-comparison`、`cost-grid`、`modal-footer`，`style.css` 对应规则；Unity `CityConstructionDecision.cs:30–54`、`CityConstructionWindow.cs:84–94,126–132`。

### 7. 候选摘要的数字、口径和颜色未形成可读比较

**源码确认。** `ConstructionImpactSummary` 用“·”拼接粮食、医疗、教育、娱乐、消费和经营净额；整个摘要只要预测成功就显示绿色，负向资源／经营变化也被染成绿色。

其中服务数字来自全街区同一步实际分配差值，不是这栋建筑的名义服务容量。但卡片只写“医疗 +…人”，容易被读作建筑能力。完整城市比较中才写实际覆盖。

候选应把主要差异对齐，标明“本建筑能力”或“本区实际覆盖变化”，逐项表达代价与收益。相同费用可集中显示；真实的不同费用仍需比较，不能一律合并。

证据：Unity `CityConstructionDecision.cs:37,62–72`；Demo `App.tsx:108` 的独立 `ComparisonTable`。升级分支已有收益／损失区分，不应误报为全部都未处理。

### 8. 公共样式把面板层级压平，图形仍被排成长列表

**实现确认；整体视觉程度需以后在 Player 对照。**

`CityMaterialStyle` 对多数非滚动区、非按钮表面统一采用 `HudRaised`，覆盖调用者要求的填色；外层、内容区、候选背景因而容易缺少层级。部分新控件会再手工设色，不能概括为所有面板都相同。

另一个偏差是布局：Demo 的容量标题与读数同行，来源图用“名称—条形—数值—操作”一行，住区用横向容量组合。Unity 多处拆成标题、读数、条、说明、整行按钮，再套带内边距的卡片；有图形也仍占用大量纵向空间。库存卡各有整行“追查月流”，施工每项有两排按钮，均加剧滚动。

证据：Demo `compact/Graphics.tsx:10,15`、`compact/graphics.css:4,7–10`；Unity `CityMaterialStyle.cs:14–35`、`CityV3Operating.cs:23–38`、`CityNavigationPages.cs:56–57`、`CityConstructionManagement.cs:25–26`、`CityInterface.cs:78–83`。

处理时应恢复各类页面自己的布局，不能再用统一卡片模板把所有工作区重排一遍。

## 三、经营工作区的内容与详表能力不完整

### 9. 政策标签没有紧凑页，且比较仅覆盖经营净额

**源码确认。** Demo 的收支／市场／政策同级标签均有侧栏工作页，政策直接列当前方案与候选、资源影响、代价与应用。Unity `policies` 没有紧凑版本，点击同级标签直接进入高级界面；返回同级标签时模式也受高级状态影响。

政策页主要比较现金流，其余效果在原始规则展开项中，没有把资源、消耗等权衡变成可读比较。实际应用命令存在，缺的是决策呈现。

证据：Demo `compact/Operating.tsx:54–55`；Unity `CityV3Workspace.cs:12–13`、`CityNavigationModel.cs:45,49`、`CityManagement.cs:25–31`。

### 10. 居民缺口追到“服务来源”后，操作链中断

**源码确认。** 当前已有住户选择与服务缺口筛选，但住户详表的提供者主要是文字及展开的凭据，没有将提供者变成可定位／检查的对象，也缺少有效供给能力和使用情况的并排比较。

Demo 的“缺口 → 受影响住户 → 提供者 → 定位／升级”流程因此没有完整接上。真实分配凭据保留下来了，不能把问题描述为模拟来源丢失。

证据：Demo `compact/Operating.tsx:30–31`、`panels/Residents.tsx:38–40`；Unity `CityNavigationPages.cs:42–45`、`CityPages.cs:85–89`。

### 11. 居民列表缺少建筑容量视角与有效排序

**源码确认。** Demo 会列出有住房的建筑，即使还没有入住，并支持按人口、健康等排列。Unity 紧凑和详细页面主要按已有住户组列出，空住宅不出现在该列表，住房容量与入住缺口难以在这里比较，也没有对应排序。

正式游戏的住户组粒度应保留；可在建筑容量列表与住户分配之间建立联动，不应照抄 Demo 一建筑一住户的简化数据模型。

证据：Demo `compact/Operating.tsx:17,30`、`panels/Residents.tsx:30–35`；Unity `CityNavigationPages.cs:41–45`、`CityPages.cs:78–86`。

### 12. 财政未接入已存在的逐建筑收入来源

**源码确认。** 财政紧凑页使用 `fiscal_ledger` 聚合项：税收只有总量，多个建筑维护项目可能都显示同一个维护标签而缺少建筑名；详表则主要把财政账目放进原始数据展开。

核心已经有 `fiscal_sources`，地块汇总与地块面板也在使用，因此不是要求增加新模拟。财政页缺的是把这些来源按建筑展示、对齐和定位。

注意：`fiscal_sources` 是既有结算总额的解释性拆分，接 UI 时不能再次加到总账，造成重复收入。

证据：Demo `compact/Operating.tsx:52`、`panels/Economy.tsx:34`；Unity `CityNavigationPages.cs:62,71–72`、`CityPages.cs:56`；核心 `Engine/Sim.cs:255–266,303`、`Presentation/TileSummary.cs:33,36–39`；现有地块呈现 `CityTilePanel.cs:108–111`。

### 13. “高级详表”仍是旧的纵向记录页

**源码确认。** 资源详表保留了真实收支与来源，但仍以资源选择器、单资源账本和纵向建筑卡片组织。Demo 的高级表支持直接比较多建筑的产出、投入、净额并定位；电力也能在同一行对照供给、需求与余量。

现有窗口更宽，并未自然获得高级表的信息效率。应保留完整记录，将适合比较的数据对齐；容量仍用条形，不把所有内容硬改为密集表格。

证据：Demo `panels/Economy.tsx:33–34`；Unity `CityPages.cs:49–63`。

### 14. 市场完整页缺少订单管理的筛选与对齐

**源码确认。** Demo 可筛全部、开放、完成、取消订单，并在同一行读方向、资源、数量、价格、总额和状态。Unity 主要倒序堆叠订单卡、显示剩余量与限价，缺状态筛选；成交历史限取最近 100 条，未提供继续查看入口。

现有真实报价、部分成交、现实在线贸易与运力规则应保留；不把 Demo 即时成交的简化机制带进正式版。

证据：Demo `panels/Economy.tsx:42–43`；Unity `CityManagement.cs:15–21`。

### 15. 施工队列难以识别多个同名项目

**源码确认。** 当前展示建筑名、新建／升级、进度与剩余材料，但缺少地块、目标等级、专业方向及运营者等识别信息。同名农居同时升级时，玩家必须逐项打开建筑才能确认。

优先级、暂停／恢复、临时施工队报价与有效期已经接通。应补齐行内身份，而不是增加施工摘要中转页。

证据：Demo `compact/Operating.tsx:66`、`panels/Construction.tsx:19–20`；Unity `CityConstructionManagement.cs:23–26,50–57`。队列汇总接口 `Economy/Construction.cs:36–38` 也需补充只读身份字段或联查现有项目。

## 四、发展、奖励与档案的移植缺口

### 16. Bonus 高级页能力反而少于紧凑页

**源码确认。** 紧凑 Bonus 有可用／已部署／全目录筛选；高级部署页左侧只列钱包和已安装对象的集合，缺少等价筛选与搜索。进入详表后，目录浏览能力反而收缩。

此外，没有库存副本时，两种界面都在生成预览之前提前返回，玩家无法先比较这个 Bonus 是否值得取得。Demo 可浏览比较并禁用安装。

已有副本安装、替换确认以及“只显示发生变化的数值”均已落实。补比较能力必须保持预览只读，不能绕过副本与费用限制。

证据：Demo `panels/Bonus.tsx:14,21,30–36`、`compact/Development.tsx:61,71–73`；Unity `CityV3Development.cs:100–102,143–159`、`CityBlueprintDesk.cs:106–112,136,146`。

### 17. 奖励选择占用了任务常用页，领取后的去向不够明确

**源码确认。** Demo 在任务里显示紧凑待领取项，点击后用独立候选窗口比较。Unity 将首个待领奖励的所有候选卡直接插入任务目标之前；候选一多，当前目标会被向下推。

领取有回执与提示，但紧凑流程缺少稳定的“留在任务／前往 Bonus 使用”结果区。完整奖励页在奖励队列空后有 Bonus 入口，不能说游戏完全没有该入口。

领取次序是正式规则，不应为了复刻 Demo 改掉。需要迁移的是窗口归属和领取后反馈。

证据：Demo `compact/Development.tsx:36`、`App.tsx:108–110`；Unity `CityV3Development.cs:29,87–93`、`CityBlueprintDesk.cs:59,95–104`。

### 18. 档案没有搜索，较旧记录缺少继续浏览入口

**源码确认。** Demo 有分类、搜索、结果数量、记录列表和正文。Unity 有分类与记录正文，但没有搜索；事件倒序只取最近 160 条，没有翻页或继续加载。

这是历史信息可达性缺口，**不是记录被删除**。不要为此补造历史或重写存档。

证据：Demo `panels/Archive.tsx:10,15–18`；Unity `CityRecords.cs:12–24`。

## 五、地图与 HUD 的上下文没有统一

### 19. 图层有颜色，却缺少可解释的固定图例

**源码确认。** Demo 有色带、范围、方向及 Shift 提示；Unity 底部主要显示图层名称、数据阶段和快捷键文字。地图源数据已有图例读数、面积与变化方向，但 HUD 没将其组织成可读的数值图例。

应绑定实际渲染的颜色尺度和单位，不直接复制 Demo 的固定范围；否则会产生新的口径错误。

证据：Demo `App.tsx:66`；Unity `CityHud.cs:146–148,204`、`CityInterface.cs:132,144`；`World/CityWorld.cs:394–400` 的图例数据。

### 20. 紧凑侧栏打开时，地图快捷键规则与 Demo 不一致

**源码确认；具体输入体验留给 Player。** Unity 的 `KeyboardOwned` 把全部打开的工作区都视为键盘占用，紧凑页也会阻止 `L／Shift+L` 和 Shift 数值切换；Demo 允许地图仍可交互时使用这些键。

Esc 路由还没有单独优先处理输入框焦点的分支，可能在输入时执行页面返回／关闭；Demo 先退出输入焦点。应明确“输入框／操作窗口独占”与“侧栏存在但地图可用”的区别。

Shift 单独按键开关和 Shift+L 避免误切本身已有实现，不能误报为仍在读条。

证据：Demo `App.tsx:49`；Unity `CityInterface.cs:26,64`、`CityMapInspection.cs:96–111`、`World/CityWorld.cs:324`。

### 21. 收起的“下一步”失去当前目标信息

**源码确认。** Demo 收起后仍显示主题、最相关条件的当前／目标值与进度，展开才增加说明和行动。Unity 收起后只剩“下一步”标题，且全局工作区打开时隐藏；展开主要给原因和入口，没有对应的进度条。

这与“默认紧凑”不冲突。应保留最小但有意义的目标状态，不重复整张任务表。

证据：Demo `App.tsx:63–64`；Unity `CityHud.cs:103–120,255–259`。

## 六、需单独决定的流程差异

### 22. 开局并未采用 Demo 的预选、回看、最后确认流程

Demo 是连续步骤，在最终确认前保留草稿。正式游戏沿用登陆点、起源等选择即执行命令，主题以后在任务中选择。这属于实际开局流程差异，不应在普通 UI 修补中擅自改玩法、增加撤销或改变随机生成时机。

若后续要求连开局也一比一，需要先明确哪些选择仅暂存、哪一步创建正式状态。当前可以确认“未移植”，不能直接认定真实开局命令错误。

证据：Demo `App.tsx:108–110`；Unity `CityPages.cs:16–23`。

另一个较小差异：Demo 的恢复演示状态有内联确认，Unity 读档／导入直接调用现有恢复命令。此处仅记录流程不一致，不据此扩展整套防误操作工程。证据：Demo `panels/System.tsx:17`；Unity `CityRecords.cs:52`、`Runtime/CityRuntime.cs:58`。

## 已落实的部分应保留

- 2K 设计基准、独立 UI 缩放和字号；固定栏目与归属。
- 全局页与地图地块面板分离，左下地块包含真实信息和操作。
- 容量条配数字、库存与月净额图形、紧凑页待结算状态。
- 栏目切换保存状态；紧凑页进入地图、选择地块、返回原工作区的路径。
- 施工与地块使用真实命令；临时施工队的叠加价格、有效期及约束。
- 独立建造／升级窗口、取消不付款、方案预览不改变 RNG、同一步比较和默认折叠的城市变化。
- Bonus 安装／替换及仅展示变化值；真实任务交付、奖励、命名、结算入口。
- 永久城市管理继续封锁、历史只读；没有擅自加回任按钮。
- UI14 图标资源与等比例处理。应以 UI14 现状继续看图标清晰度，不再拿已过时的拉伸截图作当前证据。

上述为本轮源码确认范围，不代表本轮重新完成了 Player 视觉与真人输入验收。

## 为什么以前的工程检查没有发现这些差异

现有 `Assets/Editor/V3WorkspaceChecks.cs` 的检查有价值：在隔离数据和 2K 参考画布中，覆盖多个 UI／字号组合，检查页面能生成、控件宽高为正、输入遮罩归属、部分栏目与地图返回状态，以及浏览不改变真实状态／RNG。

但它没有验证“与 Demo 同构”：

- 主要入口循环为居民、财政、施工、市场、任务、Bonus，未完整覆盖政策、档案、系统和建造窗口。
- 初始样本已经执行结算，漏掉首次结算前的实际值口径问题。
- 正尺寸与非空文本不能证明文字能读完、空间安排合理、没有遮挡，也不能证明某个设计区块存在。
- 地图用例验证紧凑页回程和详表仍打开时阻止地图输入，未覆盖详表主动定位后继续操作地块。
- 没检查“详表 → 建筑 → 返回”是否保留高级模式，也没检查任务目标落点、来源追查和候选可比性。

相关代码：`V3WorkspaceChecks.cs:87–94,98–133,138–141`。交付文档已将这些检查与截图／真人验收分开；它们不能被解释为一比一移植已完成。

根因是实现时以“页面能打开、命令能执行”为主，复用了旧页面和统一纵向组件，却没有逐区块核对 Demo 的布局、上下文和交互终点。用户负责视觉和操作体验验收，并不替代实现阶段的设计对应检查。

## 建议的修正顺序（本轮未执行）

1. **先修读数与路由。** 统一待结算口径；修通货上下文、任务目的地、实际地图定位和高级返回状态。这些问题影响玩家判断与操作结果。
2. **拿建造窗口作为首个完整对照页。** 保留真实方案与预测，把候选差异、选中后的主要效果、投入约束、固定确认区按 Demo 重排；一页对齐后再推广组件。
3. **恢复对象检查能力。** 统一对象抽屉／附属详情与地图定位，接完住户—提供者、资源—建筑、任务—处理—回目标的流程。
4. **补工作区缺失能力。** 政策紧凑页、财政建筑来源、高级比较、施工身份、Bonus 筛选与预览、奖励独立窗口、档案搜索及历史访问。
5. **统一图形与密度。** 调整表面层级、横向容量组件、来源图、图例和 HUD 目标提示。保留图形适合表达的内容，详细比较才使用完整表格。
6. **最后单独决定开局流程范围。** 不把重新设计开局规则夹带在视觉修复里。

后续工程核对应围绕真实用户路径：新开局未结算、详表定位再升级、详表检查建筑再返回、医疗目标带筛选进入居民页、财政追到建筑、奖励领取后使用 Bonus。视觉与实际鼠标键盘效果仍由用户验收；不得用检查数量代替结果。

# MET Beta 性能验证：隔离实测修复前后

**结论：停止处理和满图燃烧响应明显改善；满图结算仍产生长帧，不能宣称所有场景稳定 30 FPS。**

两次都使用同一测试脚本、相同种子与实际 App、相同 2 / 12 / 53 建筑夹具。原生测试分别运行 250.7 秒和 250.5 秒，每种密度的静态、平移、缩放、燃烧各约 20 秒。两次运行内部源文件指纹都未改变。人口约 18 / 66 / 240，起始库存为真实容量 65%。这些是显式规模夹具，不是自然经营路线。

环境：Godot 4.7.2-stable (official)，Linux X11 / Xvfb，1440×900，60 FPS 上限；llvmpipe (LLVM 19.1.7, 256 bits) 软件渲染，INTEL(R) XEON(R) PLATINUM 8573C，cgroup CPU 配额 4 核、内存上限 32 GiB。驱动不支持切换 V-Sync。两次测量均在其他 Godot 测试停止后单独运行；结果不是 M5、独立 GPU 或移动设备实测。

## 实际结算与停止处理

只调用一次真实 UI 的“返回常速”处理；其中补交尚未结算的活跃时间另列，基准没有主动添加一轮结算。总时间不含操作系统输入派发等待；进行中的长帧仍可能延迟收到点击。停止处理每个规模只有一次样本，不能冒充响应时间分布。

| 建筑 | advance_active p95 前 → 后 | 调用数 前 → 后 | 停止 UI 部分 | 停止补交时间部分 | 停止总时间 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 2 | 22.2 → 13.2 ms | 173 → 38 | 4.5 ms | 13.4 ms | 18.0 ms |
| 12 | 48.3 → 49.5 ms | 185 → 39 | 11.8 ms | 64.9 ms | 76.7 ms |
| 53 | 461.6 → 431.4 ms | 67 → 39 | 19.8 ms | 158.8 ms | 178.6 ms |

提交次数下降是这次改动的一部分；单次回调覆盖的现实时间更多，也可能由 Clock 拆成多个精确边界段。因此调用成本变化不是纯算法加速倍数。

| --- | ---: | ---: | ---: | ---: | ---: |

| 53 | 20.344947 s | 19.959540 s | 0.000000 s | 20.344951 s | -4 µs |

App 缓冲外还存在本帧距最近一次时钟采样的时间，停止回调先采样再补交；因此应比较补交后的总活跃时间，而不能把 App 缓冲字段单独当成所有尚未提交的时间。停止回调本身的 CPU 耗时不被加到此前燃烧预算。所有规模均切回常速，静态/平移/缩放保持游戏状态不变，状态校验及只读探针均通过。

最终 headless 运行 16.84 秒，通过状态与时钟检查，源指纹未变。它仍使用原样的固定 100 帧阶段；0.5 秒提交间隔使每种密度的活跃阶段只有少量结算样本，因此不使用该 headless p95 宣称帧率或稳定算法加速。原生窗口的 20 秒阶段提供本报告主要依据。

## 成本与证据边界

峰值 RSS：修复前 419.5 MiB，修复后 418.1 MiB。该数值包括全部夹具、软件渲染和测量代码，不能等同其他平台内存预算。主测试关闭自动存档以保护用户存档，存档编码另行测量，不包含磁盘 I/O。

满图独立只读探针 p95：规则编译 22.0 ms、空间投影 21.1 ms、用工分配 15.3 ms、服务分配 3.4 ms、反馈模型 0.08 ms、存档编码 52.9 ms。这些是独立调用，不能相加冒充实际 Tick 分段归因。

原生长帧仍说明全城结算成本偏高。下一轮性能工作应在目标桌面硬件重新采样，并进一步定位模拟分配/规则刷新与 UI 更新；本报告的功能 PASS 只证明状态、只读、时钟、停止模式检查通过，不等于 30 FPS 达标。

测试脚本 SHA-256 在修复前后相同，环境与渲染器相同；本次不同的受监测实现文件：`core/allocation.gd`, `ui/app.gd`, `ui/beta/interface.gd`, `ui/city032/desk.gd`。
